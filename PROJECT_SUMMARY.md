# Inspectable RAG Document Q&A Service — Project Summary (Resume/Interview Prep)

> This document was generated by auditing the current codebase file by file; every number and file reference can be re-verified in the repo. Section 8 explicitly lists what's unimplemented or partial, with no embellishment.

---

## 1. One-line description

A RAG (Retrieval-Augmented Generation) document Q&A service that deliberately avoids LangChain and stays "inspectable": plain-text documents are chunked, embedded, retrieved via FAISS, and the retrieved context is handed to an OpenAI model to produce a source-cited answer. The target user is **the developer preparing for a GenAI/RAG interview** — this is a learning/portfolio project, not a production system (in the README's own words: "a deliberately small and transparent Python project built for GenAI/RAG interview prep", see [README.md](README.md)).

## 3. Architecture, directory layout, and request flow

### Directory layout and module responsibilities

```
app/
  main.py        FastAPI app entry point: routing, lifespan management, error handling, logging
  config.py      Reads configuration from environment variables (API key, model names, chunk params, top_k)
  models.py      Pydantic data models (requests/responses/domain objects)
  ingestion.py   Text cleaning + overlap-aware character-level chunking
  embeddings.py  Embedding provider wrapper (Protocol + OpenAI implementation)
  generation.py  RAG orchestration (RagService) + grounding prompt construction + LLM call wrapper
  retrieval.py   FAISS vector store: normalization, indexing, search, persistence

  evaluate.py         Single evaluation run: 11 questions, CSV metrics output
  run_experiments.py  Comparison experiment: repeats evaluation across top_k=2/3/5 and aggregates
  questions.json      11 hand-labeled evaluation questions (with expected sources and keywords)
tests/           pytest unit tests (chunking, retrieval, service orchestration, API)
documents/       Two sample plain-text documents (employee handbook, product launch notes)
data/            Runtime-generated FAISS index + chunk metadata (gitignored)
```

### Full request lifecycle

**Write path `POST /documents`** ([app/main.py:48-58](app/main.py:48)):
1. FastAPI validates `filename`/`text` with `DocumentInput` ([app/models.py:13-15](app/models.py:13)).
2. `chunk_text()` first normalizes whitespace via regex `\s+` → single space in `normalize_text` ([app/ingestion.py:10-12](app/ingestion.py:10)), then performs character-level sliding-window chunking by `chunk_size`/`chunk_overlap`, preferring to break on whitespace to avoid splitting mid-word ([app/ingestion.py:15-48](app/ingestion.py:15)).
3. `RagService.index()` calls `OpenAIEmbedder.embed()` to batch-fetch embeddings ([app/generation.py:50-54](app/generation.py:50), [app/embeddings.py:19-32](app/embeddings.py:19)).
4. `FaissVectorStore.add()` L2-normalizes the vectors and writes them into an `IndexFlatIP` index, appending chunk metadata to an in-memory list ([app/retrieval.py:31-42](app/retrieval.py:31)).
5. On process shutdown (the teardown portion of FastAPI's `lifespan`), the index and metadata are persisted to `data/index.faiss` / `data/chunks.json` ([app/main.py:36](app/main.py:36)).

**Q&A path `POST /ask`** ([app/main.py:61-70](app/main.py:61)):
1. `AskRequest` validates question length (1–2000 characters) and an optional `top_k` (1–10) ([app/models.py:18-20](app/models.py:18)).
2. `RagService.ask()` embeds the question into a vector too ([app/generation.py:65](app/generation.py:65)).
3. `FaissVectorStore.search()` applies the same L2 normalization to the query vector, then runs FAISS inner-product search — mathematically equivalent to cosine similarity after normalization — returning the top-k `RetrievedChunk` objects (with similarity scores) ([app/retrieval.py:44-53](app/retrieval.py:44)).
4. `build_prompt()` assembles the grounding instructions, each retrieved chunk (labeled SOURCE/CHUNK/TEXT), and the user's question into a single prompt string ([app/generation.py:37-39](app/generation.py:37)).
5. `OpenAIGenerator.generate()` calls the OpenAI Responses API to produce the answer ([app/generation.py:31-33](app/generation.py:31)).
6. If the index is empty or retrieval returns nothing, a fixed "insufficient information" response is returned directly without calling the LLM ([app/generation.py:61-67](app/generation.py:61)).
7. The response includes the answer, a deduplicated and sorted list of source filenames, the full retrieved chunks (for debugging/explainability), and the end-to-end latency from query embedding through generation (measured via `time.perf_counter()`, in ms) ([app/generation.py:56-77](app/generation.py:56)).

## 4. Key design decisions and rationale

- **Vector normalization + inner product = cosine similarity**: FAISS's `IndexFlatIP` only computes inner products; the project applies `faiss.normalize_L2` on both write and query paths so the inner product becomes numerically equivalent to cosine similarity, achieving "directional similarity" semantics with the simplest index type ([app/retrieval.py:1, 13-18](app/retrieval.py:1)). This is a deliberate simplification: at scale you'd switch to an approximate nearest-neighbor index (e.g. `IndexIVFFlat`/HNSW), but for an interview-sized dataset, `IndexFlatIP` (exact brute-force search) is sufficient with controllable latency.
- **The grounding prompt strongly constrains hallucination but doesn't guarantee it away**: the prompt explicitly requires "answer only from the provided context" and outputs a fixed sentence when information is insufficient ([app/generation.py:15-19](app/generation.py:15)). As the README states, this only reduces hallucination risk, it's not a guarantee — if retrieval picks the wrong chunks, the source document itself is wrong, or the model doesn't fully follow instructions, the answer can still be flawed. That's why `retrieved_chunks` and similarity scores are returned alongside the answer, for inspection ([README.md](README.md)).
- **Provider boundaries are abstracted with `Protocol`**: both `Embedder` and `Generator` are defined as `typing.Protocol` ([app/embeddings.py:10-11](app/embeddings.py:10), [app/generation.py:22-23](app/generation.py:22)), and `RagService` depends only on these interfaces rather than the OpenAI SDK directly. This lets `tests/test_service.py` fully exercise the orchestration logic offline with `FakeEmbedder`/`FakeGenerator`, with no real API key or network call needed ([tests/test_service.py:8-17](tests/test_service.py:8)).
- **Consistency/concurrency handling is deliberately simplified**: the vector index and chunk metadata live only in **single-process memory** (`FaissVectorStore` is a plain Python object, [app/retrieval.py:21-29](app/retrieval.py:21)), persisted once on FastAPI `lifespan` startup (`load()`) and shutdown (`save()`) ([app/main.py:26-27, 36](app/main.py:26)). This means: no transactions, no write locks, each process/instance in a multi-process deployment maintains its own unsynced index, and a crash loses every write since the last clean shutdown. This is an explicit trade-off favoring readability and interview explainability over engineering-grade data consistency (see sections 8 and 9).
- **The error-handling strategy is "fail fast and translate to an HTTP error"**, not retry/degrade: both `/documents` and `/ask` wrap the underlying SDK calls in `try/except Exception`, log, and translate failures into `502` (provider failure) or `422` (validation failure, e.g. an empty question) ([app/main.py:53-58, 64-70](app/main.py:53)). There's no timeout handling, no retry/backoff, no circuit breaker — callers must handle OpenAI API rate limits or timeouts themselves.
- **The chunking algorithm favors readability over semantic completeness**: it splits by a fixed character count and falls back to breaking on whitespace, using overlap to preserve a bit of cross-boundary context ([app/ingestion.py:26-47](app/ingestion.py:26)). It's simple but insensitive to structures like long sentences or code blocks, since it does no sentence- or paragraph-aware semantic chunking.

**Offline evaluation** (not unit tests — effectiveness evaluation against the real OpenAI API, requires an API key):
```bash
python -m evaluation.evaluate --chunk-size 800 --overlap 150 --top-k 3
python -m evaluation.run_experiments
```
The evaluation set is the **11 hand-labeled questions** in [evaluation/questions.json](evaluation/questions.json), covering both sample documents (7 questions on the employee handbook, 4 on the product launch notes). Four metrics ([evaluation/evaluate.py:39-52](evaluation/evaluate.py:39)):
- `retrieval_success`: whether the expected source document appears in the top-k retrieval results.
- `answer_keyword_match`: whether the answer contains preset keywords — **a rough proxy for correctness, not a substitute for human review** (the README's own words).
- `faithfulness_proxy`: whether those same keywords also appear in the retrieved context, measuring minimal traceability of the answer — not a rigorous faithfulness metric.
- `latency_ms`: end-to-end time from query embedding to generation completion.

A recorded real run (2026-08-14, `chunk_size=800, overlap=150, top_k=3`): source retrieval success **100%**, keyword answer match **100%**, faithfulness proxy **100%**, average end-to-end latency **2395 ms** (CSV at [evaluation/results/results_chunk800_topk3.csv](evaluation/results/results_chunk800_topk3.csv)). The top-k comparison experiment (top_k=2/3/5) showed 100% quality metrics across the board on this 11-question dataset, with average latencies of roughly 2121/1410/1513 ms respectively ([evaluation/results/top_k_experiment.csv](evaluation/results/top_k_experiment.csv)) — **the correct conclusion is "this dataset is too small to reveal any effect of top-k on quality," not "top-k doesn't affect quality,"** a point the README itself also makes.

## 8. What's unimplemented or only partially implemented (stated plainly, no embellishment)

- **No Dockerization, no CI/CD pipeline at all** (no `Dockerfile`, no GitHub Actions, etc.). The deployment method described in the README is limited to local `uvicorn --reload`.
- **~~`.env.example` didn't actually exist~~ — now added.** The README's quickstart previously said `cp .env.example .env` while that file was missing, a docs/repo mismatch that's since been fixed.
- **No real data consistency or concurrency guarantees**: the index is a pure in-memory object, read/written to disk only on process startup/shutdown ([app/main.py:26-27, 36](app/main.py:26)); multiple worker processes, concurrent writes to `/documents`, or an abnormal process exit (e.g. killed) are all unhandled — no locks, no WAL, no atomic writes.
- **Only `.txt` plain text is supported.** A code comment itself notes "PDF can be a future extension" ([app/ingestion.py:52](app/ingestion.py:52)); PDF/Word/HTML parsing is unimplemented.
- **No authentication/authorization, no rate limiting**: anyone who can reach the service can arbitrarily read/write the index and consume OpenAI API quota.
- **No timeout, retry, or circuit-breaker handling for OpenAI API calls**: `OpenAIEmbedder`/`OpenAIGenerator` call the SDK synchronously and translate any error directly to a 502, with no exponential backoff retry.
- **No incremental update/delete for documents**: `FaissVectorStore` only has `add()`, with no method to delete or update by chunk id; clearing the index means manually deleting the files under `data/`.
- **No multi-turn conversation/session history**: `/ask` is stateless single-turn Q&A, with no support for context-aware follow-up questions.
- **The evaluation set is very small** (11 questions, 2 sample documents); the README itself stresses that 100% metrics don't show that the top-k parameter has no effect on quality — only that this dataset lacks the discriminating power to show it. **Don't put "100% accuracy" on a resume as a generalizable result** — state honestly that it's "results on an 11-question evaluation set."
- **`faithfulness_proxy` and `answer_keyword_match` are both simple keyword-matching proxies**, not semantic-level correctness/faithfulness evaluation (e.g. LLM-as-judge or human annotation), as the code comments themselves note ([evaluation/evaluate.py:44-46](evaluation/evaluate.py:44)).
- **No vector-database-level scalability**: `IndexFlatIP` is exact brute-force search; retrieval latency grows linearly as data scale increases (e.g. millions of chunks), with no approximate nearest-neighbor index or external vector database (e.g. Milvus, pgvector, Pinecone) introduced.

## 9. Technical points likely to come up in an interview

- **"Why an inner-product index instead of an L2-distance index?"** — See [app/retrieval.py:1, 13-18](app/retrieval.py:1): because the vectors are L2-normalized, the inner product is mathematically equivalent to cosine similarity; without normalization, `IndexFlatIP` ranking would also be affected by vector magnitude and would no longer be a pure semantic-similarity measure.
- **"What happens if two worker processes receive a `/documents` request at the same time?"** — A race condition: each process maintains its own in-memory index and writes its own `data/` files, and whichever writes last overwrites the other — a real, unresolved gap in the current architecture (listed in Section 8). This is a good opening to discuss migrating to an external vector database plus database locking/optimistic concurrency control.
- **"What are the limitations of the chunking strategy?"** — Pure character-count splitting is unfriendly to structured text (code, tables, lists), and long sentences can be split across semantic boundaries; alternatives include sentence/paragraph/token-based chunking, recursive character splitting, or semantic chunking.
- **"Does the grounding prompt really prevent hallucination?"** — Not entirely; it only reduces the probability. The model may not fully follow instructions, retrieval itself may surface the wrong chunks, or the source document may contain incorrect information. The evaluation's `faithfulness_proxy` is only a keyword proxy — real faithfulness evaluation needs human review or a stronger LLM-as-judge.
- **"What's the effect of increasing `top_k`?"** — Higher recall, but also a longer prompt (higher token cost, possible context-length limits), more noise (irrelevant chunks can confuse the model), and higher latency. The README's comparison experiment data is a good discussion point, with the honest caveat that this small dataset doesn't reveal a quality difference.
- **"Where does the 2395ms latency actually go?"** — The code's `latency_ms` only measures query embedding + retrieval + LLM generation as a whole ([app/generation.py:60-71](app/generation.py:60)), without breaking out embedding call time versus chat generation time separately. If pressed on "can latency be optimized," good talking points include streaming responses, embedding caching, and async concurrent handling of multiple requests — none of which are currently implemented.
- **"What are this system's capacity limits — how much data/concurrency can it handle?"** — Single process, in-memory index, exact brute-force search: fine for demo-scale datasets (the current sample documents total roughly 292 words, per `wc -w` on `documents/*.txt`), not suitable for production-level concurrency or large document collections, which would require redesigning along the lines listed in Section 8 (external vector store, async task queue, auth, observability).
